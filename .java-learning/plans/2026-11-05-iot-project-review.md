## 第一条候选：物模型模板分页查询

这个功能是第一条带读候选，不涉及一开始就向真实设备下发动作。

静态已核对的部分：

1. DMP 的 ModelTemplateController.page 接收模板名称、状态、页码和每页数量，并把结果转换为 API 响应。
2. QueryModelTemplatePageService.page 校验分页范围与允许状态，调用 ThingModelTemplateQueryPort。
3. HubThingModelTemplateQueryAdapter.page 通过 Hub 客户端查询，处理远程异常和业务错误，并转换返回结构。
4. Hub ThingModelTemplateService.page 使用仓储查询模板，再按模板 ID 批量取得聚合数据并组成分页结果。

还未核对完整的 Bean 装配、远程接口映射、鉴权上下文、仓储实现与最终 SQL，也未执行这条链路。

### 带学时需要回答的问题

- 这个列表到底展示什么，查询条件和状态分别有什么业务含义？
- 参数在哪一层校验，非法页码或状态如何反馈给前端？
- Controller 注入的用例接口由哪个实现/配置装配？
- 为什么 DMP 通过 Hub 客户端而不是自己直接查询这些业务表？
- 远程超时、空响应、业务错误分别在哪处理？
- Hub 的批量聚合如何实现，实际 SQL 次数是多少？
- 自己新增筛选条件时，哪些接口、对象、查询与测试必须一起修改？

这些问题先用源码定位和调用链推演回答；运行相关结论保留为未验证，性能或生产指标不填入讲解材料。

## 建议的推进方式

1. 先完成当前 Redis 的必要学习与小验收，不一次跳到四服务全量架构讲解。
2. 每周两次、每次约1小时源码带读，包含在总学习预算内，不打通公司环境。
3. 从上述只读查询链路开始，补齐接口映射、Bean 装配、仓储与 SQL 的静态定位。
4. 每条链路按“业务问题 → 请求/对象 → 核心机制 → 操作 → 结果”讲解。
5. 推演一次需求改动，例如新增筛选条件，列出需要变更的接口、对象、查询与测试，不要求修改公司源码。
6. 再选创建/发布等状态流转、权限或异步中的1–2条链路，是否存在以源码为准。
7. 最终形成2–3张调用链图、关键类索引、异常路径和3–5分钟讲解，分别标记源码事实、推断与未验证项。实际编码与运行能力在天机学堂验收。
