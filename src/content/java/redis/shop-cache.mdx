## 二、先理解缓存解决的问题

### 1. 缓存是访问数据时的中间层

缓存是存放数据副本的临时位置，通常具有较高的读写性能。它让后续请求有机会直接使用已经准备好的结果，减少对较慢数据来源的访问。

在 Web 应用中，浏览器可以缓存资源，Java 应用可以使用进程内缓存或 Redis，数据库内部也会使用缓冲机制。P35 通过这些位置说明缓存的普遍性；本篇真正编写的是 **Java 应用访问 Redis 的业务缓存**。

商铺查询加入缓存后，逻辑关系如下：

```text
浏览器发出商铺查询
        ↓
Controller → Service
                ↓
           查询 Redis
           ├─ 命中 → 返回缓存中的商铺
           └─ 未命中 → 查询 MySQL
                         ├─ 查到 → 写入 Redis → 返回商铺
                         └─ 未查到 → 按本阶段的空值策略处理
```

浏览器不会直接连接 Redis。缓存判断、数据库查询和回填都由后端业务代码完成。

### 2. 为什么值得缓存商铺详情

商铺详情页会显示名称、地址、图片、营业时间等信息，课程通过按 ID 查询详情的接口演示缓存。重复访问同一家商铺时，不必每次都重新查询数据库并组织相同结果。

主要收益是降低数据库负载、减少重复查询的响应时间，提高系统承接请求的能力。收益取决于命中率、数据变化频率、网络与查询开销，不能把视频中的一次耗时对比当成所有环境的固定性能指标。

引入缓存也有三类成本：

| 成本 | 在商铺案例中的表现 |
| --- | --- |
| 一致性 | MySQL 已修改，Redis 还保存着旧的名称或地址 |
| 开发维护 | 查询增加命中判断、回填、TTL、空值处理；写操作需要使缓存失效 |
| 运维与资源 | 需要 Redis 内存、部署监控及故障防护，规模扩大后还可能需要高可用部署 |

**重点：先判断业务需要，再决定缓存范围。** 对读请求少、数据经常变化且查询本身很便宜的业务，缓存未必能抵消新增成本。

## 四、给商铺详情添加缓存

### 1. 找到原始调用链

原始 `ShopController` 的详情查询直接调用 `shopService.getById(id)`。这个方法来自 MyBatis-Plus 的 `IService`，最终查询数据库。

加入缓存后，需要在查询前后增加多个分支，业务应移到 Service：

```text
GET /shop/{id}
    → ShopController.queryShopById
    → IShopService.queryById
    → ShopServiceImpl.queryById
    → 先 Redis，必要时再 getById 查询 MySQL
```

**易错点：** 如果 Controller 仍调用 `getById`，新写的 `queryById` 就不会执行，缓存不会生效。

### 2. 约定缓存结构与键名

课程这里选择 Redis String，value 是商铺对象的 JSON：

```text
key   = cache:shop:1
type  = String
value = 商铺 JSON
```

ID 保证同一类商铺键的区分，`cache:shop:` 前缀区分其他业务。不能所有商铺共用 `cache:shop`，也不能读时用 `cache:shop:1`、删时却拼成 `shop:1`。

String 和 Hash 都可以表达对象；本段选择 String 是为了演示手动 JSON 转换，**JSON 内容不会把 Redis String 自动变成 Hash**。客户端与序列化基础参见 [Redis Java 客户端与完整建项](/docs/java/redis/java-clients/)。

### 3. 添加常量和接口声明

## 六、缓存更新策略与并发顺序

### 1. 三类更新方式

| 方式 | 触发条件 | 一致性与代价 | 本案例的使用方式 |
| --- | --- | --- | --- |
| 内存淘汰 | 达到配置的内存限制，并按淘汰策略处理 | 对应用较透明，但无法保证某条旧数据及时更新 | 理解 Redis 内存管理，不能用它代替业务失效 |
| 超时剔除 | 键的 TTL 到期 | 实现简单；TTL 内仍可能读到旧值 | 给商铺缓存添加 30 分钟 TTL |
| 主动更新 | 业务写入数据时主动处理缓存 | 需要编码、处理失败与并发；能更及时反映修改 | 更新商铺数据库后删除对应缓存 |

低变化、容忍短期旧值的数据，可以采用较简单的过期方案；商铺详情等需要较及时更新的数据，课程采用主动更新，并用 TTL 限制异常情况下旧数据的存续时间。

> **准确性补充：** 内存淘汰取决于 `maxmemory` 和 `maxmemory-policy`；`noeviction` 策略不会自动淘汰键，而会对相关写入返回错误。不能把课程对淘汰机制的概括理解为“Redis 默认必然自动删旧缓存”。详见 [Redis 键淘汰说明](https://redis.io/docs/latest/develop/reference/eviction/)。

TTL 到期后也不会自动替应用查询 MySQL。它让旧键不能继续命中，下一次请求进入回源逻辑时才重建缓存。

### 2. 主动更新的三种模式

| 模式 | 谁维护缓存与数据库 | 主要特点 |
| --- | --- | --- |
| Cache Aside，旁路缓存 | 应用分别读写数据库和缓存 | 可控性较高，需要自己编写失效与回填逻辑；本案例采用 |
| Read/Write Through | 由统一的数据访问服务封装缓存与数据库 | 调用者较简单，但服务内部需要实现一致性处理 |
| Write Behind，异步写回 | 应用先写缓存，后台异步持久化 | 可合并写入、提高吞吐；存在同步延迟和未落库数据丢失风险 |

后三者不是三个 Redis 命令，而是数据访问模式。P38 主要用它们说明为什么本案例选择由业务代码控制的 Cache Aside。

### 3. 为什么修改后删除缓存

数据库写入后，可以选择更新缓存，也可以删除缓存。课程选择删除，使下次读请求按需重建。

连续修改多次、期间没有人读取时，每次计算并写入缓存可能产生多次没有被使用的更新；删除后按需回填，可以减少这种工作。删除也把读取所需的数据组织逻辑留在查询路径中。

这里的“删除”必须使用读缓存时相同的键。删除返回未找到，不一定表示失败，目标键可能本来就不存在。

### 4. 为什么先更新数据库，再删除缓存

先删缓存的风险，可以用两个并发请求表示：

```text
初始状态：数据库名称为 A，缓存也为 A

写请求：删除缓存 ───────────────────→ 数据库改为 B
读请求：           缓存未命中 → 查到 A → 写回 A

结果：数据库是 B，缓存又保存了 A
```

因此本案例采用：

```text
写操作：更新数据库 → 删除缓存
读操作：查缓存 → 未命中时查数据库 → 写缓存并设置 TTL
```

**注意：这一顺序仍不等于绝对没有竞态。** 如果读请求先读到旧数据库值，随后写请求更新数据库并删除缓存，读请求最后才把旧值写入缓存，仍会暂时不一致。P38 通过时序比较认为后一种窗口通常更小，并使用 TTL 限制旧值保留时间。

## 七、实现商铺修改后的缓存失效

### 1. 给正常商铺缓存设置 30 分钟 TTL


### 3. 在 Service 实现更新和删除

课程演示的核心结构如下：

```java
@Override
@Transactional
public Result update(Shop shop) {
    Long id = shop.getId();
    if (id == null) {
        return Result.fail("店铺id不能为空");
    }

    updateById(shop);
    stringRedisTemplate.delete(CACHE_SHOP_KEY + id);
    return Result.ok();
}
```

导入 `org.springframework.transaction.annotation.Transactional`。先校验 ID，再更新数据库，最后删除缓存。`updateById` 是 MyBatis-Plus 已提供的方法，`update(Shop)` 则是本段新增的业务方法。

> **事务边界补充：** 保留课程的 `@Transactional` 结构便于复现，但默认 `StringRedisTemplate` 不参加 Spring 托管事务。Redis 删除抛出未捕获运行时异常时，数据库事务可能回滚；已经成功执行的 Redis 删除不会跟随 MySQL 自动恢复。即使开启 Redis 事务支持，也不能据此把两套存储当成具有严格原子提交保证的一个事务。相关默认行为可对照 [Spring Data Redis 事务文档](https://docs.spring.io/spring-data/redis/reference/redis/transactions.html)。

另外，`updateById` 返回的是更新是否成功。为了让独立练习更容易发现“ID 根本不存在”，可以在该调用处做下面的检查，再继续删除缓存；这是本篇的防错补充：

```java
boolean updated = updateById(shop);
if (!updated) {
    return Result.fail("店铺不存在或更新失败");
}
```

不要把补充检查与原来的 `updateById(shop)` 同时保留成两次调用。

课程的用户页面没有商家后台的编辑入口，因此使用 Postman 发送更新。也可以使用下面的 PowerShell 请求。

先记录练习商铺的原始名称，然后查询 `/shop/1`，使 `cache:shop:1` 存在。只在可修改的练习数据库中执行下列更新，它会修改 ID 为 1 的商铺名称：

```powershell

Invoke-RestMethod `
```

## 八、缓存穿透：为不存在的商铺保存短期标记

### 1. 穿透为什么会持续访问数据库

缓存穿透指请求的数据在缓存和数据库中都不存在。第一版查询遇到不存在的 ID，只返回“店铺不存在”，不保存任何结果。

因此每次请求都会重复：

```text
不存在的 ID → Redis 未命中 → MySQL 查不到 → 返回错误
下一次相同 ID → 仍然 Redis 未命中 → 仍然查 MySQL
```

大量此类请求会绕过缓存的保护。**普通缓存未命中不等于穿透**：数据库中存在、只是尚未缓存的数据，查到并回填后就可以正常命中。

### 2. 两种方案的差异

| 方案 | 做法 | 优点 | 需要注意 |
| --- | --- | --- | --- |
| 缓存空对象 | 数据库查不到时，在对应键保存“不存在”标记 | 简单，重复无效查询能命中标记 | 不同无效 ID 仍会消耗键空间；短期内新增同 ID 数据可能受旧标记影响 |
| 布隆过滤 | 在查询链路前判断 ID 是否可能存在 | 空间效率较高，可提前拦截大量不存在请求 | 有误判；需要初始化、维护与同步，不能只接一个方法就完成 |

布隆过滤可以理解为利用多个哈希位置和位数组表示集合成员关系。**在数据已正确加入、过滤器状态正确的前提下，判断“不存在”可以排除，判断“存在”只代表可能存在。** 误判放行后，数据库仍可能查不到。

> **概念补充：** Redis Bitmap 提供位操作能力，不等于 Bitmap 本身已经实现了一个完整布隆过滤器。本段只比较思路，不实现布隆过滤。

课程编码选择缓存空对象，同时用较短 TTL 限制无效键的保留时间。若后来新增了先前被标记为不存在的数据，应处理相应空值缓存，不能一直等着错误标记自然消失而不考虑业务要求。

### 3. 严格区分三种读取结果

本案例使用 **空字符串 `""`** 表示“数据库已确认不存在”：

| Java 读取结果 | Redis 状态 | 业务含义 | 下一步 |
| --- | --- | --- | --- |
| `null` | 键不存在 | 还没有可用缓存 | 查询数据库 |
| `""` | 键存在，值为空字符串 | 已缓存“不存在”的结果 | 直接返回店铺不存在 |
| 非空 JSON | 键存在，值为商铺 JSON | 已缓存正常数据 | 转回 Shop 并返回 |

空字符串不是 Java `null`，也不是文本 `"null"`。不要把 `null` 直接传给 `set`，也不要先把空字符串当 JSON 对象反序列化。

`StrUtil.isNotBlank` 对 `null`、空字符串、空白内容都返回 false。因此只有第一个 `isNotBlank` 判断仍然不够：还必须拦截已经命中的空值，避免继续向数据库查询。

### 4. 最终版常量

保留其他业务已有常量，在 `RedisConstants` 中确保具有以下定义。本篇空值有效期取 2 分钟：

```java
public static final String CACHE_SHOP_KEY = "cache:shop:";
public static final Long CACHE_SHOP_TTL = 30L;
public static final Long CACHE_NULL_TTL = 2L;
```

正常商铺缓存保留 30 分钟，空值标记保留 2 分钟。短 TTL 可以降低无效数据积累和短期不一致的影响，但不能拦住不断更换 ID 的所有无效请求。

### 5. 最终版详情查询方法

用下面的方法 **替换前面第一版 `queryById`**，不要保留两个签名相同的方法。原有注入字段和类继承关系不变。

```java
@Override
public Result queryById(Long id) {
    String key = CACHE_SHOP_KEY + id;

    // 1. 正常数据命中：JSON 转对象后直接返回。
    String shopJson = stringRedisTemplate.opsForValue().get(key);
    if (StrUtil.isNotBlank(shopJson)) {
        Shop shop = JSONUtil.toBean(shopJson, Shop.class);
        return Result.ok(shop);
    }

    // 2. 非 null 说明命中了空值标记，不再查询数据库。
    if (shopJson != null) {
        return Result.fail("店铺不存在！");
    }

    // 3. 真正的缓存缺失，才回源查询。
    Shop shop = getById(id);
    if (shop == null) {
        stringRedisTemplate.opsForValue().set(
                key, "", CACHE_NULL_TTL, TimeUnit.MINUTES);
        return Result.fail("店铺不存在！");
    }

    // 4. 数据库存在，缓存真实结果并设置有效期。
    stringRedisTemplate.opsForValue().set(
            key, JSONUtil.toJsonStr(shop),
            CACHE_SHOP_TTL, TimeUnit.MINUTES);
    return Result.ok(shop);
}
```

本段需要的完整业务导入为：

```java
import cn.hutool.core.util.StrUtil;
import cn.hutool.json.JSONUtil;
import com.hmdp.dto.Result;
import com.hmdp.entity.Shop;
import java.util.concurrent.TimeUnit;
import static com.hmdp.utils.RedisConstants.CACHE_SHOP_KEY;
import static com.hmdp.utils.RedisConstants.CACHE_SHOP_TTL;
import static com.hmdp.utils.RedisConstants.CACHE_NULL_TTL;
```

**两处修改缺一不可：** 数据库查不到时写入空字符串；读取后识别空值并提前返回。只做前者，`isNotBlank("")` 仍为 false，请求依然会落到数据库。

### 6. 用不存在的 ID 验证

视频使用 ID `0` 演示，先确认练习表中没有这条记录：

```sql
SELECT id, name FROM tb_shop WHERE id = 0;
```

如果确实不存在，在同一个练习 Redis 中删除可能残留的标记：

```redis
SELECT 0
DEL cache:shop:0
```

重启应用后请求：

```powershell
Invoke-RestMethod 'http://localhost:8081/shop/0' |
    ConvertTo-Json -Depth 10
```

应返回 `success: false` 和店铺不存在的信息。第一次允许出现一条 `tb_shop` 查询，然后检查：

```redis
EXISTS cache:shop:0
TYPE cache:shop:0
GET cache:shop:0
STRLEN cache:shop:0
TTL cache:shop:0
```

预期依次为：键存在、String、空字符串、长度 0、剩余 TTL 为不超过 120 的非负秒数。**Redis CLI 中的 `""` 与 `(nil)` 含义不同。** 同时结合 `EXISTS`、`TTL` 判断，避免仅凭空白显示误判。

在 2 分钟内再次请求 `/shop/0`，应仍返回不存在，但不再出现对应数据库查询。空值到期后再次请求，允许重新查一次数据库，再建立新的短期标记。

如果已有参数校验会直接拒绝 `0`，可选择另一个已经确认不存在且符合参数规范的 ID。为了复现空值缓存流程，应先说明请求被哪一层拒绝，不要把参数校验直接返回当成 Redis 命中。

### 7. 主动防范措施

P41 还提出：合理设计 ID、做基础格式校验、加强访问权限管理、限制请求频率和热点参数访问。这些与空值缓存配合使用，可以更早挡住无效请求。

本阶段没有实现登录权限改造、限流组件或 ID 生成器。ID 难猜也不能替代权限检查；这里掌握的是防护方向，不需要为完成本段缓存实验同时引入一整套微服务组件。

## 九、缓存雪崩：大量缓存同时不可用

### 1. 两种典型触发条件

缓存雪崩指同一时段大量缓存失效，导致许多请求集中访问数据库。课程分析两种来源：

1. 大量键在相近时间过期，例如批量预热时给所有键设置相同 TTL。
2. Redis 服务故障，原本由缓存承接的请求失去缓存保护。

Redis 故障时，客户端可能抛出连接异常或超时；**并不会由 `StringRedisTemplate` 自动把请求改为查询 MySQL**。是否回源取决于应用的异常和降级策略，但没有控制地把故障请求全部转向数据库，会带来雪崩风险。

### 2. 分情况选择措施

| 触发原因或目标 | 处理思路 | 为什么有效 |
| --- | --- | --- |
| 大量键一起到期 | TTL 添加随机偏移 | 把过期时间分散，减少同一时刻的集中回源 |
| 单个 Redis 节点故障 | 主从、哨兵等高可用措施 | 降低单节点故障让整个缓存服务长时间不可用的概率 |
| 缓存整体故障或回源压力过大 | 限流、隔离、降级、必要时快速失败 | 限制数据库承接的请求量，保护核心服务 |
| 需要更多层次承接热点请求 | 多级缓存 | Nginx、JVM 本地缓存等其他层可以承接部分请求 |

主从复制与故障转移不能理解成“任何故障都零中断、零丢失”；多级缓存也需要维护各层的数据更新。这里掌握其作用，搭建和具体实现属于后续课程。

### 3. TTL 随机偏移示例

> **复现补充：** P42 给出随机 TTL 思路，没有带着完成 Java 代码。下面将 30 分钟加 0～5 分钟随机量，结果为 30～35 分钟，便于理解和自行练习。

```java
long ttlMinutes = CACHE_SHOP_TTL
        + ThreadLocalRandom.current().nextInt(0, 6);

stringRedisTemplate.opsForValue().set(
        key, JSONUtil.toJsonStr(shop),
        ttlMinutes, TimeUnit.MINUTES);
```

需要导入 `java.util.concurrent.ThreadLocalRandom`。`nextInt(0, 6)` 包含 0，不包含 6。

如果采用此练习，再验收正常商铺 TTL 时，应按不超过 2100 秒的范围判断，不能仍要求固定接近 1800 秒。**随机 TTL 缓解的是多键集中到期，不能解决 Redis 整体故障，也不能代替对单个热点键的重建控制。**

## 十、缓存击穿：热点键失效后的重建竞争

### 1. 与穿透、雪崩的区别

缓存击穿也称热点 Key 问题。一个或少数热点键失效后，在缓存重建完成之前，大量并发请求都未命中，于是一起访问数据库。

课程强调两个特征：**访问并发高**，而且 **缓存重建较复杂、耗时较长**。重建可能包含多张表查询、关联计算和数据组织，而不只是一次简单的主键查询。

```text
热点键过期
    ↓
请求 A：查库并重建 ───────────────────→ 写回缓存
请求 B：      未命中 → 也查库
请求 C：          未命中 → 也查库
请求 D：              未命中 → 也查库
```

重建窗口内没有可用缓存，即使每次请求的逻辑单独看都正确，并发回源仍可能压垮数据库。

### 2. 方案一：互斥锁控制重建

基本流程为：

1. 查询缓存，命中则返回。
2. 未命中时尝试获取该键的重建锁。
3. 拿到锁的请求负责查询数据库、构建结果并写入缓存。
4. 其他请求获取失败，短暂休眠后重新查询缓存或重试。
5. 重建完成并释放锁后，等待者能命中新缓存。

```text
请求 A：未命中 → 拿到锁 → 查库重建 → 写缓存 → 释放锁
请求 B：未命中 → 获取失败 → 等待 → 重新查询 → 命中
请求 C：未命中 → 获取失败 → 等待 → 重新查询 → 命中
```

核心目的是让同一热点键的重建由受控请求完成，避免所有请求同时回源。请求重新拿到锁时也应考虑缓存可能已经建好，具体代码与锁的异常释放在后续实现时处理。

优点是思路直接，不需要在业务缓存中新增逻辑过期字段；代价是其他请求需要等待，重建越慢，等待越明显。锁使用不当还会带来阻塞与死锁风险。

> **一致性边界：** 这里偏向让请求等待重建结果，避免主动返回已经逻辑过期的旧值。但一把重建锁不能自动保证所有数据库修改和缓存更新的严格强一致；锁的保护范围、并发写入和失败处理仍然需要单独分析。

### 3. 方案二：逻辑过期并异步重建

对提前准备的热点数据，逻辑过期方案不依赖 Redis TTL 到期删除，而是把业务过期时间存到值中：

```text
cache:shop:1
    ├─ data：商铺数据
    └─ expireTime：业务判断使用的过期时间
```

`expireTime` 是普通业务字段，不是 Redis 的 TTL。查询时由应用把它与当前时间比较。

流程为：

1. 预先把热点数据写入 Redis，同时保存逻辑过期时间。
2. 查询命中且未逻辑过期，直接返回。
3. 发现逻辑过期，尝试获取重建锁。
4. 获取成功，安排独立线程查询数据库、重建缓存并刷新逻辑过期时间；完成后释放锁。
5. 当前请求直接返回旧数据。
6. 其他请求发现过期且拿不到锁，也直接返回旧数据。
7. 后续请求在异步重建完成后读到新数据。

```text
请求 A：读到旧值 → 发现过期 → 拿锁 → 提交重建任务 → 返回旧值
后台线程：                            查库 → 写新值和新时间 → 释放锁
请求 B：读到旧值 → 发现过期 → 拿锁失败 → 返回旧值
请求 C：后台更新完成后查询 → 返回新值
```

**难点：两种方案都可能用锁，区别在于是否等待重建。** 逻辑过期方案通过允许短期旧值，让请求不用等待数据库重建任务。

不设置 Redis TTL 也不保证键永远存在：它仍可能被删除、淘汰或因故障丢失。因此方案依赖热点数据准备与实际未命中处理，不能把“逻辑过期”理解成“以后永远无需查数据库”。

### 4. 两种击穿方案如何选择

| 比较项 | 互斥锁重建 | 逻辑过期与异步重建 |
| --- | --- | --- |
| 重建期间的请求 | 等待、休眠重试，再读重建结果 | 尽快返回已有旧值 |
| 响应延迟 | 可能随重建时间上升 | 前台请求较少受到重建耗时影响 |
| 数据新鲜度 | 倾向等待本轮重建结果 | 明确接受短期旧数据 |
| 缓存值结构 | 普通业务数据即可 | 要额外保存逻辑过期时间 |
| 实现代价 | 管理重建锁与等待 | 还要管理过期判断、后台任务和更新 |
| 适用取向 | 更在意重建后的数据新鲜度，能接受等待 | 热点数据允许短时旧值，更在意请求可用性与延迟 |

P43 的目标是理解上述取舍。到本篇结束时，商铺查询已经有 TTL 和空值缓存，**还没有加入互斥锁或逻辑过期的 Java 实现**；不要把理解方案当成项目已经具备了击穿防护。

### 3. 按现象定位问题

| 现象 | 优先核对 | 处理方向 |
| --- | --- | --- |
| Maven 无法编译、找不到 Hutool 或 MyBatis-Plus | 是否导入原始 POM、依赖是否下载完成 | 先修复依赖，不用新版本替换全部组件 |
| 实体 getter 不被识别 | Lombok 与注解处理 | 检查 IDE、Maven 编译的实际错误 |
| MySQL 连接拒绝或表不存在 | 主机、端口、库名、SQL 导入结果 | 先跑通 `tb_shop` 查询 |
| Redis 超时、NOAUTH 或 WRONGPASS | 实际 Redis 主机、监听端口、密码、网络 | 让 CLI 与 Java 对齐同一连接目标 |
| Java 写了缓存，RDM 看不到 | 实例、端口、数据库编号、是否刷新 | 统一为应用使用的实例和 DB0 |
| 每次都查 `tb_shop` | Controller 是否仍调用 getById、键是否一致 | 让接口进入新 queryById，并检查键是否被频繁删除 |
| 缓存值存在却 JSON 转换失败 | 键是否被其他练习写过、缓存值是否正常 JSON | 先读 GET 确认内容，再只删除该练习键重建 |
| 加了 TTL，现有键仍为 -1 | 是否一直命中改动前的旧缓存 | 删除指定键，触发一次回源写入 |
| 更新名称成功，但页面仍旧 | 更新接口是否调用新业务、删的键是否正确 | 直接核对 MySQL、Redis 和接口响应三者 |
| 更新后观察到键仍然存在 | 是否已刷新详情页触发重建 | 更新后立即检查删除，再发起查询 |
| 返回 200，但实际没有修改 | Result.success、请求方法、JSON、ID | 检查业务结果和 UPDATE 是否实际执行 |
| 空值已经写入，重复查询仍有 SQL | 是否遗漏 `shopJson != null` 分支 | 在回源前拦截空值；不要只检查 isNotBlank |
| 不存在的 ID 第一次就无 SQL | 参数校验、拦截器、已有空值缓存 | 先确认真实路径，再判断缓存是否生效 |
| 前端 404 或代理接口错误 | Nginx 工作目录、root、/api/ 前缀 | 直接测 8081，再测 8080 的代理路径 |
| 详情页仍出现优惠券 SQL | SQL 查询的具体表 | 只判断商铺详情 SQL，不把其他接口混为一谈 |

| 问题 | 典型数据状态 | 数据库压力来源 | 本段处理 |
